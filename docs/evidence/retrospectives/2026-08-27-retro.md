# Retrospective — initial adapter skill

Date: 2026-08-27

## What worked

- Freezing the target-project file contract before writing the skill kept the helper,
  references, and acceptance checks aligned.
- Running generated manifests against the real pinned JSON Schema caught defects that
  unit tests and plugin validation could not see.
- Keeping declaration, protocol, semantics, and binding as separate verdicts prevented a
  valid JSON document from becoming a false compatibility claim.

## Error cycles

1. The first exact-schema invocation used top-level `await` under `tsx -e`; its CJS
   transform rejected the code. The helper now wraps validation in an async function, and
   all three profiles exercise the same integration path.
2. The first scaffold used `replace-me` for identity method. That made the template useful
   as a visible placeholder but invalid against the method enum. It now chooses `tls` for
   remote defaults and `local-install` for stdio/local defaults while leaving runtime
   identity verification unclaimed.
3. Contract-schema failures were initially copied into the local-structure gate. The
   checker now keeps those gates independent and returns a failure if either executed gate
   fails.
4. The first MCP template always chose streamable HTTP. The helper now exposes MCP mode,
   executable reference, and runtime args so an existing stdio server is preserved rather
   than silently remodelled.

## Carry-over

- Run the trigger and behaviour dataset through a fresh model once an evaluation
  model/account pool is explicitly selected.
- Add live negotiation and semantic-probe harnesses only in the future Fabric host/SDK;
  do not simulate admission inside this authoring skill.
