# Retrospective: the sweep as 0.49.0 (FAA-111)

Run stamp: 2026-10-24. Six releases (0.47.0 to 0.48.3) had each passed their own unit reading; this run read them
together at the seam and product tiers, then closed FAA-60, FAA-88 and FAA-89.

## Where the run diverged

1. **A unit reading per release does not see what releases do to each other.** The seam reading over six releases found
   a regression a single release introduced (0.48.2's `_resume_next` kept the queue head while resuming, so a handler
   that settled inside the resume ran twice) and a second implementation of a rule one release changed (the OpenRouter
   ceiling still counted a subscription's estimate after DEC-0110 changed the usage report). Neither was visible in the
   diff that caused it. **Next time:** after a run of releases on one area, read them together at the seam tier before
   the next feature, and grep for every other implementation of a rule a release changes.
2. **A fix that moves a side effect later can open a re-entry.** FAA-86 moved "take the request off the queue" from
   before the resume to after it, so a lost answer kept it first; the resume itself could reach the code that resumes
   the queue. **Next time:** a queue head is taken before the work and put back on failure, never held across a call
   that can re-enter the queue.
3. **The kit version bump before `build` was missed a third time** (0.41.0, 0.47.0, 0.49.0). A regex written for two
   spaces of indentation met `kit.json`'s one, matched nothing, and the build wrote the new digests under 0.48.3. The
   released-history test would have caught it at the end of the suite; restoring the file from `main` fixed it.
   **Next time** is no longer a habit: `fabric_kit.py build` refuses to rewrite the digests of a version with a release
   tag (`test_build_refuses_to_rewrite_a_released_version`).
4. **A timing test under a load average of 430.** One Node case and seven Python cases failed in the full suites and
   passed alone; the Node case also passed three times under the same parallel load on both this branch and `main`.
   Re-running alone before calling a test red (the 0.47.0 lesson) held; the case that waits a fixed 20 ms is FAA-114.
5. **What held:** each fix's test was seen failing first; the trigger evals ran before the descriptions changed and
   again after, so the description edits are measured, not guessed; the scenario for FAA-60's pointer was written
   before the hook changed.
