# 0.69.0 brief: the question after a gate decline (FAA-224) and the Fabric.app order (FAA-229)

Status: implemented on branch `agent/faa-0.69.0`, 2026-11-06. Wave 1 of the machine-move gaps
(`docs/evidence/specs/2026-11-06-machine-move-gaps.md`, G6) and the follow-up of 0.68.0's gate decline.

## Decisions

- D1 (FAA-224). After step 3's decline `com.reply`, the run asks the operator once with `fabric_question_ask`:
  `kind: access`, `about: board.gate.<capability>`, a `commandId` the contract names, and a `text` naming the request,
  the gate and what opens it; it waits for no answer. Source: Fabric's proposal (board thread `1add3c03`, `5fb4226d`)
  and its answer `a58b4280` (2026-11-06): the tool is on every Fabric session's surface, launched or enrolled, with no
  slot or `board.respond` needed, 0.3.16 included; `about` is a topic key, so an operator decision under it settles
  later questions without asking, but two open questions with one `about` stay two; a `commandId` derived from the
  board request id makes a retry return the same question.
- D2. The `commandId` is computed by the hook, not by the run: `gate_question_id(request)` = UUID v5 of the name
  `board.gate` in the namespace of the request id (`fabric_session_cli.py`). A run cannot compute a UUID v5 reliably
  in its head; rendering it costs 36 characters. Not the request id itself, which another ask may reuse as its own key.
- D3. A failed question is left: the decline already answered the request, so the close (step 6) does not wait on it.
- D4 (characters). The conditional contract at its longest stayed at 3996 (3994 before D6) with the step added (122
  characters) by shortening clauses no test pins: "nobody watches", "takes the lease", the step 1 reads in
  parentheses, step 3's enroll and claim in parentheses, "finish before run-ends-at" folded into the state clause,
  "After the lease, claim and reply", "(add `open`, `done`, `notes`; no value)", the helper line, "With other values",
  step 5's complete as `(observed: true)`.
- D5 (FAA-229). macOS candidates in the launcher's order: `~/Applications/Fabric.app` first, then
  `/Applications/Fabric.app`; `find_fabric_bin`, which only `status` calls, takes a copy outside the user's home only
  when its owner is this user or root (an install every user shares; one rule, `another_users_copy`, for proposing
  and for flagging). The launcher's order is the same after its PR #277 (open on 2026-11-06; launcher 0.2.75 still
  uses `/Applications`); it installs its own copy unless the user owns and can write `/Applications`, because it
  updates the bundle; the adapter only runs it. The hooks and the worker run the
  registered command, so `status` flags a registered `fabric-mcp` that is another user's copy (a bare command by what
  PATH finds, a link by its target) and proposes installing the user's own copy first when there is neither the user's nor root's, then
  re-registering it; a project-scope entry is overridden with a local one, never removed. Other platforms are
  unchanged.
- D6 (readings round 1). The contract's question names its `text` (Fabric refuses an empty one); "what opens it" is a
  Fabric release with CO-506 on 0.3.16, since Agent access only decides a request a service filed; a failed question
  goes into the closing notes (the reference). "never complete what you did not observe" left the contract (steps 4 and 5 say
  `observed: true`, and the reconcile rule asks an observed result) to make room: 3996 at the longest.

- D7 (readings round 2). `status` never proposes the `<Fabric>` placeholder: with no copy of the user's own it
  says to install one into `~/Applications` first. Root's copy is accepted for proposing too (the round 1 change to
  skip it told a pkg or MDM install to install Fabric).

- D8 (readings round 3). `status` says "put your own Fabric.app in ~/Applications" (no claim about the released
  launcher), prints "none of yours" on macOS whenever neither the user's nor root's copy is found, and SKILL.md Step 2 names the
  replacement of another user's registration; a relative command with a folder is not judged; a local entry is
  replaced by a local one in the same folder (a user one would lose to a project's); `shutil` and `uuid` are imported
  where they are used, so the hooks load neither (seam reading 3).

- D9 (readings round 4). The session-hooks paragraph keeps the start rule exact (the down line only in a project
  that uses Fabric) and "act on it once"; the local and project lines name the folder `claude_registration` found
  the entry in.

- D10 (readings round 7). Fabric's `board.read-at-start` rule after its CO-517 (main `603da12f`, in no release yet)
  asks every session refused at `com.enroll`, not only a run, so a live session asks too: `fabric_session.py gate-id
  <request>` prints the run's `commandId` (a model cannot compute a UUID v5 reliably, D2), and
  `references/project-board.md`'s live-session rule and the board-answer eval say so.
