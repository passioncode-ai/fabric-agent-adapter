# 0.74.0 brief: the listener's owner before a credential (FAA-226, DEC-0154 HA-2)

The contract accepted DEC-0154 on 2026-11-07 and released it as `v0.1.0+2026-11-07.1` (`18f8d487`, PR #248; board
thread `1fe66e6e`, message `f6d0a09a`). HA-2 (`docs/specification/service.md#ha-2` at the tag): before a client sends
any credential to `http://127.0.0.1:<port>`, and before a host reports a local service healthy, it establishes that the
server end of its connection belongs to a process of its own OS account, from the computer's socket table. A listener
of another OS account, root's, SYSTEM's or a service account's, or one whose owner cannot be told, is `foreign-user`:
nothing is sent and nothing it answers is read as the service's. The order of states is `down`, `foreign-user`,
`foreign`, then the well-known `status`. The well-known `process.pid` is never proof.

The row comes from the operator's instruction relayed on thread `1fe66e6e` (2026-11-05), filed before the pause on new
tasks (spec `docs/evidence/specs/2026-11-06-machine-move-gaps.md`, G2 and G3) and waiting only on this tag, as the
other projects on that thread took theirs (Fabric CO-514, Fabric Dashboards, the launcher's PC-152).

## Decisions

- D1. One module tells the owner: `fabric_peer_owner` at L0, standard library only. Its Python file is Project
  Observatory's `peer_owner.py` 1.1.0, written to be vendored by commit (public repository
  `passioncode-ai/project-observatory-dashboard`, commit `f86f0622`, the same licence, AGPL-3.0-only OR
  LicenseRef-PassionCode-Commercial). It differs in its docstring's provenance paragraph and in `Owner` and `Row`,
  NamedTuples where it has frozen dataclasses: a dataclass with postponed annotations needs its module in
  `sys.modules`, and the kit's own test loads every module by its path without one
  (`test_every_module_loads_by_path_from_any_folder`), built in the functional form with real types so their generated
  `__new__` resolves its annotations (`test_annotations.py`), and `Optional[X]` for `X | None` in signatures (the 3.9
  floor's `typing.get_type_hints` cannot read the union). It reads macOS through
  `sysctl net.inet.tcp.pcblist_n` (calibrated on a connected pair of its own, else `netstat -anv`), Linux through
  `/proc/net/tcp` and `/proc/net/tcp6`, Windows through `GetExtendedTcpTable` and the owner's token SID. The check is on
  the connection the request then travels on (`server_end` of the connected socket), not a look at the port before
  connecting, so no listener can change between the check and the request; `CheckedHTTPConnection` checks again on
  every reconnect `http.client` makes.
- D2. The Node twin `fabric-peer-owner.mjs` is new code with the same questions (`listener`, `serverEnd`, `peer`,
  `refusal`, `checkedSocket`, and `CheckedAgent`, an `http.Agent` whose every new socket is checked): Node has no ctypes, so macOS reads `netstat -anv -p tcp` and `ps -o uid=` (Observatory's
  documented fallback, measured about 20 ms), Linux the same `/proc` files, Windows `netstat -ano -p TCP` (and TCPv6)
  for the pid and a PowerShell `GetOwnerSid` (`Win32_Process`) for its owner's SID, against `whoami /user`'s SID; a
  process whose SID cannot be read is an owner that cannot be told. SIDs, never names (unit reading 1: a name in the
  console's code page decodes to one string for two accounts). The parsers
  that both twins have read the same fixtures under `test/fixtures/peer-owner/`.
- D3. Every kit client that sends a credential to loopback checks first, and a refusal sends nothing:
  - `check_service.py`: a new first rule for a local placement, `listener.owner`: `PASS` when this OS account's process
    listens, `FAIL` `foreign-user` (another account's, root's or one that cannot be told) and no further rule reads the
    port, `NOT_RUN` when nothing listens (then `well-known.answers` fails as `down`, as before). Every local request
    goes through `CheckedHTTPConnection`.
  - the hub client (`fabric_hub.post_mcp`, `postMcp`): `HubError("foreign-user")` before the bearer, retryable: Fabric
    may come back on its port and every retry checks again; the live `pid` in `hub.json` stays a precondition and is
    never the proof. The Node client keeps its checked connection alive (`CheckedAgent`, free sockets closed after 2 s,
    under a Node server's 5 s keep-alive), since a reading of the table costs about 35 ms in Node (netstat) where
    Python's sysctl costs about 4 ms; the board's own timing tests needed it (the test hub now keeps HTTP/1.1
    connections, as Fabric's does).
  - `fabric_http.request` (and its Node twin) for an `http://` URL on a loopback host: the same check on its
    connection, `foreign-user` as the error's code; HTTPS and other hosts are unchanged.
  - `check_dashboard_layout.mjs` before it asks a local origin for a login code, through `fabric-http.mjs` imported when
    it runs; a copy of that file alone (its own tests copy it so) sends nothing to a local origin.
- D4. The installers' poll (`fabric_supervisors` wait for the well-known answer after a start) succeeds only on a
  listener of this OS account; a listener of another account is `foreign-user`, never a successful install (service.md
  Lifecycle table, "Install").
- D5. Fail closed everywhere: `unknown` (a table that cannot be read, two rows, a process gone) is `foreign-user` with
  its reason, as HA-2 says ("one whose owner cannot be told"). A reason names the owner's kind, method and reason,
  never anything the listener answered.
- D6. The contract pin moves to `18f8d487` (`v0.1.0+2026-11-07.1`) from `eac1a594`. Between them only DEC-0154: prose in
  `service.md` and its neighbours, schema descriptions, `device-enrollment`'s optional `hostLabel` (HA-4) and its
  vectors, the contract's own channel-agent test (its vectors unchanged). `eac1a594` joins
  `SUPPORTED_CONTRACT_COMMITS` and the validator's previous pins.
- D7. Out of this release, each its own row: FAA-227 (HA-3, a kit service refuses another account's loopback peer
  before reading its request), FAA-225 and FAA-230 (HA-1, the port and its claim file, after CT-228's schema and
  reference with vectors), FAA-228 (services without an open session, CT-234).

- D8 (readings, round 2). `listener.owner` reads the server end of a connection of the probe's own, on which nothing
  is sent, not a look at the port: two sockets of one account on one port (SO_REUSEPORT workers) read as that account,
  where the look read `several-rows`. `classify` and `classify_sid` (both twins) ask for this process's own uid or SID
  before the system rule, so a client running as root or SYSTEM owns root's or SYSTEM's listener; launchd's pid 1 stays
  `system`. The vendored file differs there too, and its header says so.

- D9 (readings, rounds 3 to 5, and the board). On Linux `/proc` prints a connection not yet accept()ed with uid 0 and
  inode 0. `server_end` reads an accepted connection's own row (the uid of the process that accepted it) and, for an
  unaccepted one, the listener row on its local address (exact, else wildcard); `peer` reads an inode-0 client row as
  `unknown` (`closed`). Reading only the listener row for every server end (`9e42341d`) let a listener swapped after
  another account accepted the client pass (Project Observatory, thread `ced00f6e`): the hybrid is Observatory's
  `peer_owner.py` 1.2.0 reading; the contract's CT-254 is settling the wording (FAA-258).

## Acceptance

- A listener of another uid (the fixtures' socket tables, read by both twins) gets no credential and reads
  `foreign-user`; an empty port stays `down`; this account's own listener passes (spec G2).
- The hub client sends no bearer to a hub port whose listener is not this account's (spec G3).
- A real pair on this machine reads `this-account` on both ends in both twins.
- `npm test`, `test/validate.py` and both `claude plugin validate --strict` pass.
