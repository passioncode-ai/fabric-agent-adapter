# 0.66.0 brief: a dispatched run closes its workflow only once its request is settled (FAA-213)

passioncode-vesta's finding (board thread `1add3c03`, 2026-11-05): `references/on-demand-session.md` closed the
workflow on an error the run cannot get past (a refused claim and the like), though the request may still be `queued`
or `claimed`; a closed workflow there makes Fabric's next dispatch fail at the take-back (`boardDispatchRun.ts`,
Observatory `WorkflowClosed`) on every cycle. Fabric's spec §3.4 leaves the workflow open for an unsettled run, and
Fabric agreed on the board (CO-409).

## Decisions

- D1. The rule is Vesta's: close the workflow only once the request is settled (the board accepted the complete or a
  reconcile, or `com.get` reads it answered, terminal or `outcome_unknown`); otherwise leave it open, with a
  checkpoint without `close` naming the reason when the run holds the lease.
- D2. The exit contract the session hook prints gains the rule in one sentence and points to the reference for the
  rest. It must stay under Hermes' 4000 characters at its longest (the existing test); two explanations move out of
  the contract to the reference, which already holds them (`on-demand-session.md` lines on the packet's
  `credentials`, the `pack` and the latest body). No rule is dropped.
